## 失败案例 1：「一天有多少秒」——答案并非来自检索 ⭐ 最典型

**问题**：
```
请问一天有多少秒？
```

**现象**：

系统答对了（"一天有86400秒"），但看【依据】就发现问题了：

```
[1] 第2章 块#5   距离 1.1406   ← 文档头（标题+封面+目录）
[2] 第5章 块#25  距离 1.2369   ← 文档头
[3] 第4章 块#19  距离 1.2480   ← 文档头
```

**top-3 全是各章的文档头，没有一个是含答案的页面。**

而真正写了答案的是**第2章第3页**：

```
一天有24小时、一小时有60分钟，一分钟有60秒，
因此，一天就有24×60×60=86400秒……
```

**期望**：
应检索到第2章第3页那个块，并在【依据】中展示出来。

**归因**：

**检索层问题**，具体是「文档头万能块霸榜」：

1. Markdown 被切分后，每个文档的第 0 块总是包含
   「文件名 + source 注释 + 封面页 + 目录」
2. 这类块含大量通用词汇（章节标题、课程名），
   **与任何问题都"有点像"**，因此在向量空间里跟什么查询都靠得近
3. 结果它稳定占据 top-1/top-2，把真正含答案的块挤出去

**更深层**：语料只有约 40 个块，5 个文档头就占 **12.5%**，
在小语料里这个污染比例被放大。

**验证**：

```bash
# ① 确认预处理没丢内容（答案确实在 Markdown 里）
grep -n "86400" data_processed/*第2章*.md
# → 找到：「一天就有24×60×60=86400秒」

# ② 确认检索没命中它
python eval.py --retrieval-only
# → 用例3「一天总共有多少秒」的 top-3 全是文档头
```

**两条证据合起来**：内容在库里，但检索没找到它
→ **问题定位在检索层，不是预处理层，也不是生成层**

**改进**：

在 `build_index.py` 的 `split_documents()` 后新增 `filter_header_chunks()`，
按两条规则丢弃文档头/封面块：

```python
# 规则1：短块 + 含 source 注释 → 文档头
if len(text) < 200 and "<!-- source:" in text:
    drop()

# 规则2：封面特征命中 2 处以上 → 封面页
#   特征：邮箱 / 讲解: / 编制: / ——系列——
if len(cover_re.findall(text)) >= 2 and len(text) < 300:
    drop()
```

**改进后验证**（本地模拟分块，74 块）：

```
过滤后保留：64 个
丢弃：10 个        ← 5 个文档头 + 5 个封面页
过滤后仍含封面特征的块：0     ← 清理干净
含 '86400' 的块：1 个         ← ✅ 答案块未被误删
```

## 失败案例 2：「变量类型」——有答案却拒答（假阴性）

**问题**：
```
请问C语言中的变量类型有哪些？
```

**现象**：
```
【回答】抱歉，我无法从提供的资料中找到相关信息来回答此问题。
（判定原因：LLM 判定资料不足以回答）

【检索到的片段】
  [1] 第2章 块#8 （距离 0.5340）
      ## 第 8 页 ### 2.5 常量和变量
      ...类型名指定变量的数据类型，"="为赋值符号...
```

**注意**：检索到的块**明显相关**（在讲变量和数据类型），
距离 **0.5340** 还是全部用例里最小的之一，但 LLM 拒答了。

**期望**：
基于该块作答，例如说明"资料中提到变量定义需指定类型名，
并举例 int arrCircleVal 等"，同时说明资料未给出完整类型清单。

**归因**：

**生成层问题** —— Prompt 约束过紧。

原 Prompt：
```
请确保你的回答完全基于这些上下文，不要使用上下文之外的知识。
如果上下文中没有足够的信息来回答问题，请直接告知：...
```

两重强约束（"**完全**基于" + "**不要**使用外部知识"）让模型过度保守：
它认为资料没给出 int/float/char 的**完整清单**，就判定"信息不足"而拒答。

**验证**：

```bash
python main.py
> 请问C语言中的变量类型有哪些？     # 拒答
> 这个C语言的开发环境是怎么样的？    # 正常作答（4个要点，有据可查）
```

同一套约束，有的问题能答有的拒答 —— 说明**不是检索问题，
而是模型对"够不够回答"的判断阈值太严**。

**改进**：

改写 Prompt，把绝对约束改为相对约束，并明确允许"部分回答"：

| 改前 | 改后 |
|---|---|
| 请确保回答**完全基于**上下文 | 请**优先使用**上下文信息 |
| **不要使用**上下文之外的知识 | 不要**编造**上下文中不存在的内容 |
| 信息不足就拒答 | 提供了**部分**信息就作答，**并说明未涵盖的部分** |
| — | 只有**完全不涉及**才拒答 |
| — | 回答时**引用片段编号**便于核对 |

**权衡**：放宽约束有增加幻觉的风险，故保留了"不要编造"的底线，
并要求引用片段编号以便追溯。

## 失败案例 3：相似度距离完全无法区分「有答案 / 无答案」

**现象**：

汇总 `eval_baseline.txt` 的 top-1 距离：

| 用例 | 问题 | 实际有无答案 | top-1 距离 |
|---|---|---|---|
| 3 | 一天总共有多少秒？ | ✅ **有** | **1.1406** |
| 4 | 秒值的取值范围是多少？ | ✅ **有** | **1.0346** |
| 7 | Python 的装饰器怎么用？ | ❌ 无 | **1.0579** |
| 9 | React 的 useEffect？ | ❌ 无 | **0.8104** |
| 6 | 数组和函数有什么关系？ | ✅ **有** | 0.6676 |

**关键矛盾**：
- 用例 3（有答案）距离 **1.1406** > 用例 7（无答案）距离 **1.0579**
- 用例 9（完全无关，React）距离 **0.8104** < 用例 6（有答案）距离 **0.6676**

**排序完全错乱**：「有答案」的距离普遍比「无答案」还大。

**期望**：
有答案的查询，其 top-1 距离应显著小于无答案的查询。

**归因**：

1. **L2 距离本身没有归一化** —— LangChain 的
   `similarity_search_with_score` 返回的是**原始 L2 距离**，
   不是 0~1 的相似度，数值大小受向量模长、文本长度影响
2. **语料太小**：约 40 个块，任何问题都能找到"相对最像"的块，
   绝对距离失去区分意义
3. **文档头块污染**：它们的向量跟所有查询都接近，
   进一步压缩了有效区分区间

**验证**：

```bash
# 距离数值与"是否真的有答案"无相关性
python eval.py --retrieval-only | grep "距离"
```

**结论与改进**：

**该指标在本数据集上不可用** —— 所以 `config.score_threshold` 保持 `None`
（不启用阈值过滤）。

**若要做基于阈值的拒答，应改用**：
- **余弦相似度**（先归一化，映射到 0~1，与人直觉一致）
- 或引入 **Rerank 模型**（交叉编码器直接给相关性分数，远比向量距离可靠）
- 或扩大语料规模，让距离分布重新变得有意义

**这个案例本身很有价值**：它说明**"给阈值"不是万能的**，
必须先验证指标是否具备区分能力，再决定是否使用。

## 失败案例 4：跨章节重复块「抱团」霸榜（v2 实测新暴露）

**问题**：
```
请问C语言是什么？
```

**现象**：

改进后的 top-4 全部是**不同章节的同一个页面**：

```
[1] 第3章 块#32  距离 0.7771
    ## 第 9 页 ### 4.本章任务 任务1：2020年总共有366天...
[2] 第4章 块#43  距离 0.7782
    ## 第 13 页 ### 4.本章任务 任务1：2020年总共有366天...
[3] 第2章 块#23  距离 0.7816
    ## 第 16 页 ### 4.本章任务 任务1：2020年总共有366天...
[4] 第5章 块#53  距离 0.7831
    ## 第 11 页 ### 4.本章任务 任务1：2020年总共有366天...
```

**注意距离：0.7771 / 0.7782 / 0.7816 / 0.7831** —— 四个数字几乎相同，
说明它们的向量**高度相似**，在向量空间里「抱团」，
互相抬高了排名，把真正相关的块挤出 top-k。

**期望**：
这类页面不含知识点（只是实验任务描述），不应该出现在检索结果里。

**归因**：

**检索层问题**，与案例 1 是同一类根源 —— **跨章节重复 + 信息量低**。

但成因不同：
- 案例 1 是**分块产物**（文档头是切分时自动产生的）
- 案例 4 是**素材本身**（讲义每章都有相同的"本章任务"页）

5 份 PPT 是同一门课的系列讲义，模板高度统一，
所以「本章任务」页逐字重复。这是**素材的结构性特点**，
不是 bug —— 但需要在索引阶段处理。

**验证**：

```bash
grep -c "2020年总共有366天" data_processed/*.md
# → 5 个文件里都有，证实跨章节重复
```

**改进**：

`filter_header_chunks()` 增加规则 3：

```python
TASK_PATTERNS = [
    r"###\s*\d+\.\s*本章任务",          # 编号小标题「4.本章任务」
    r"本章任务\s*任务\d",                # 正文「本章任务 任务1」
    r"任务1[:：]\s*2020年总共有366天",   # 逐字重复的模板句
]
```

**★ 关键设计：习题页不过滤。**

「5.本章习题」页看似同类，但它含**知识点问句**：

```
5.本章习题
（1）为什么要使用函数？
（2）什么是内部函数？
```

这些**本身就有检索价值**（问"为什么要用函数"时，这页就是相关证据）。
所以规则**只针对"本章任务"**，不动"本章习题"。

**改进后验证**（本地模拟分块，74 块）：

```
过滤后保留 60 个
  文档头 5 + 封面页 5 + 任务页 4 = 丢弃 14 个

关键检查：
  残留重复任务句块：0 个              ← 清理干净
  含「本章习题」的保留块：10 个        ← ✅ 未被误杀
  含 86400 的块：1 个                 ← ✅ 答案块保留
  含「枚举就是把可能的值」的块：1 个   ← ✅ 保留
  含「为什么要使用函数」的块：2 个     ← ✅ 保留
```

## 汇总：四个案例的层次分布

| 案例 | 层次 | 根源 | 改进手段 |
|---|---|---|---|
| 1. 文档头霸榜 | **检索层** | 分块产物 | 过滤文档头块 |
| 2. 有答案却拒答 | **生成层** | Prompt 过严 | 放宽约束 + 允许部分回答 |
| 3. 距离指标失效 | **评估层** | 指标未归一化 + 语料小 | 不用该指标，改用余弦/Rerank |
| 4. 重复块抱团 | **检索层** | 素材结构重复 | 过滤模板化任务页 |

**四个案例覆盖了 RAG 的三个不同环节** —— 这是本项目最有价值的产出：
**失败不是笼统的"效果不好"，而是能被定位到具体层次。**

**特别值得注意**：案例 1 和案例 4 都属"检索层"，
但**根源完全不同**（一个是分块产物，一个是素材特点）。
这说明**同层次的失败也需要分别归因，不能一概而论**。
